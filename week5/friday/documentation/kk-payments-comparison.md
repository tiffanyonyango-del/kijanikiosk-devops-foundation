# Blue/Green Deployment vs Container-Based Deployment

## Introduction

The KijaniKiosk payments service can be deployed using several approaches. Two useful approaches are blue/green deployment and container-based deployment. Both improve reliability compared with making changes directly to a live application, but they solve different problems. Blue/green deployment focuses primarily on switching between two complete application environments, while containerization focuses on packaging the application and its runtime dependencies consistently.

## Comparison

| Concern                  | How the blue/green approach addresses it                                                                                                                                                                                                          | How the container approach addresses it                                                                                                                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Deployment mechanism** | Two separate environments are maintained: one serves the current version while the other receives and is tested against the new version. Traffic can then be switched to the new environment once it is ready.                                    | The application and its required runtime are packaged together as a container image. The payments service was deployed as two identical instances, providing a consistent environment for each running copy.                                                                                     |
| **Rollback mechanism**   | Rollback can be very fast because traffic can simply be switched back to the previous environment if the new version fails validation or causes problems.                                                                                         | Rollback is achieved by deploying a previously built and versioned image. Because each image is associated with a specific application version and source revision, an earlier known-good version can be restored.                                                                               |
| **Failure recovery**     | If the new environment fails before traffic is switched, the existing environment can continue serving users. Once traffic has been switched, recovery depends on the availability of the previous environment and the traffic-routing mechanism. | Multiple application instances can continue serving requests if one instance fails. During testing, deleting a running payments instance caused the platform to automatically create a replacement. The replacement reached a running state in **57 seconds**, demonstrating automatic recovery. |
| **Scaling**              | Scaling generally involves creating additional complete environments or adding capacity to the active environment. This can provide strong isolation but may require more infrastructure and resources.                                           | Multiple container instances can be created from the same image. The payments service was configured with two instances, allowing the workload to continue if one instance becomes unavailable and providing a foundation for increasing capacity.                                               |

## Evidence from the Payments Service

The container-based deployment demonstrated several practical benefits during testing. The payments service successfully ran with two instances, and both were reachable through the service. When one instance was deliberately deleted, the deployment automatically created a replacement. The measured recovery time from deletion to the replacement becoming ready was **57 seconds**.

The production image was also optimized using a multi-stage build and an Alpine-based runtime environment. The resulting image was approximately **236 MB** according to the container engine's reported image size. This did not meet the original target of less than 100 MB, despite the optimization work. The available evidence also shows the earlier Node Bookworm base image at approximately **1.63 GB**, illustrating the substantial difference between the large development/runtime base environment and the much smaller production image. The 100 MB target should therefore be considered an optimization goal that was not fully achieved rather than a claim of compliance.

## What Containerization Does Not Yet Solve

Containerization improves consistency, portability, and deployment repeatability, but it does not by itself provide complete orchestration. Running multiple containers introduces additional concerns such as automatically replacing failed instances, distributing traffic, scaling according to demand, managing service discovery, and coordinating deployments across multiple machines. These capabilities become increasingly important as an application grows.

The next project, focused on Kubernetes orchestration, addresses these limitations by providing a platform for managing containerized workloads. It can automatically maintain the desired number of application instances, route traffic to healthy instances, replace failed instances, support service discovery, and provide mechanisms for scaling. In this project, the payments service already demonstrated some of these orchestration benefits, particularly automatic recovery and service-based access. Kubernetes therefore builds on the consistency provided by containers and adds the operational control required to run them reliably at scale.
